Lesson 1 of the mini-OpenCode mission

The Agent Loop

Everything else you'll build (persistence, permissions, tool registries) is scaffolding around one small loop. Learn the loop first, on a model running on your own machine.

The claim

An "AI coding agent" sounds like it needs a lot of machinery. At its core, it doesn't. Thorsten Ball built a working one that reads, lists, and edits files in about 400 lines, mostly boilerplate. The loop itself is maybe 20 of those lines.

Everything OpenCode adds on top (durable sessions, permission prompts, many providers, retries) exists to make this loop safe and durable, not to replace it.

The loop itself

  1. You send the model the conversation so far, plus a list of tools it may use. Each tool is a name, a description, and a JSON Schema for its arguments.
  2. The model replies. Sometimes that's just text. Sometimes it's a request to call one or more tools: structured data naming each tool and the arguments to call it with.
  3. If it's a tool request, your code runs the tool (reads the file, lists the directory). The model never executes anything itself.
  4. You append the tool's result to the conversation and go back to step 2.
  5. Eventually the model replies with text and no tool request. That ends the turn.
Why this shape The model can only propose actions; your code is always the thing that does them. That boundary is the only safety an agent has, and it's why OpenCode's permission system exists at all.

Anthropic's "Building effective agents" makes a related point: the teams that succeeded mostly used this loop directly, not elaborate frameworks. (Its tooling details are dated, and the page itself says so, but the loop is not.)

Three words before you start

You'll run this loop against three sources of models, so keep these apart from day one (full definitions in the glossary):

  • A provider serves models over HTTP: Ollama, a llama.cpp server, or Anthropic.
  • A protocol is the wire format of a request and its response. Ollama and llama.cpp both speak OpenAI Chat Completions; Claude speaks Anthropic Messages.
  • A model is a specific set of weights, like qwen3.5:9b.

One provider can speak several protocols, and several providers can share one. Your clone uses two protocols for three providers. That's also how OpenCode reaches local models: its Ollama support only discovers models, and every call goes through its generic OpenAI-compatible protocol (plugin/provider/local.ts).

What a tool call looks like on the wire

Here is the OpenAI Chat Completions version, which you'll use for both local providers. These shapes were captured from Ollama 0.40.13 and llama.cpp b11669 running qwen3.5:9b: 

// You POST to {base}/v1/chat/completions:
{
  model: "qwen3.5:9b",
  messages: [{ role: "user", content: "What files are in this directory?" }],
  tools: [{
    type: "function",
    function: {
      name: "list_files",
      description: "List the files in a directory…",
      parameters: { type: "object", properties: { path: { type: "string" } }, required: ["path"] }
    }
  }]
}

// The reply's choices[0].message:
{
  role: "assistant",
  content: "",
  tool_calls: [{
    id: "call_0mnjckd1",
    type: "function",
    function: { name: "list_files", arguments: "{\"path\":\".\"}" }   // a JSON *string*
  }]
}

// You append that message, run list_files("."), then append:
{ role: "tool", tool_call_id: "call_0mnjckd1", content: "README.md\nsrc\n…" }

That's the whole contract. The agent is a while loop around this exchange, plus functions that actually do list_files. Note that arguments arrives as a string you must JSON.parse.

Your turn: build the loop

Do this in its own folder, outside this repo: it's the seed of your mini-OpenCode clone. Plain TypeScript and plain fetch, no SDKs and no Effect yet, so every byte on the wire is visible to you.

  1. Install Bun (this Mac doesn't have it yet): curl -fsSL https://bun.com/install | bash, open a new terminal, check bun --version (Bun docs).
  2. mkdir my-agent && cd my-agent && bun init -y.

Ollama: the main path

  1. Start Ollama with a 32k context. Its default is only 4k tokens on machines with under 24 GiB of VRAM, and Ollama itself says agents need far more (context length docs). An agent's history and tool results overflow 4k within a few steps. Quit the Ollama app first, then: 
    OLLAMA_CONTEXT_LENGTH=32768 ollama serve
  2. In another terminal: ollama pull qwen3.5:9b (about 7 GB, with tool support).
  3. Write list_files(path) first as a plain function from a path to a string (use readdir from node:fs/promises). It has nothing to do with the API.
  4. Write the loop: POST to http://127.0.0.1:11434/v1/chat/completions with your messages and one tool. Push the reply's message onto messages. If it has tool_calls, run each one and push a role: "tool" message per call. If it doesn't, print content and stop.
  5. Prove it: ask "What files are in this directory?" with a console.log inside list_files, so you can see your function ran instead of the model guessing.

Expect each step to take several seconds on a 16 GB M1. That's the model working, not your code hanging.

Stuck? A minimal working loop 
import { readdir } from "node:fs/promises"

const BASE_URL = process.env.BASE_URL ?? "http://127.0.0.1:11434/v1"
const MODEL = process.env.MODEL ?? "qwen3.5:9b"

const tools = [{
  type: "function",
  function: {
    name: "list_files",
    description: "List the files in a directory. Use it whenever you need to know which files exist. Returns one name per line. Pass '.' for the current directory.",
    parameters: { type: "object", properties: { path: { type: "string" } }, required: ["path"] },
  },
}]

const listFiles = async (path: string) => {
  console.log(`[list_files] ${path}`)
  return (await readdir(path)).join("\n")
}

const messages: unknown[] = [{ role: "user", content: process.argv[2] ?? "What files are in this directory?" }]

while (true) {
  const response = await fetch(`${BASE_URL}/chat/completions`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    body: JSON.stringify({ model: MODEL, messages, tools }),
  })
  const message = (await response.json()).choices[0].message
  messages.push(message)
  if (!message.tool_calls?.length) {
    console.log(message.content)
    break
  }
  for (const call of message.tool_calls) {
    const input = JSON.parse(call.function.arguments)
    messages.push({ role: "tool", tool_call_id: call.id, content: await listFiles(input.path) })
  }
}
Under the hood: Ollama's own protocol

Ollama also speaks a native protocol at /api/chat (tool calling docs). It's worth seeing once, because it shows that the details are choices, not laws:

  • arguments arrives as an object, not a JSON string.
  • Tool calls have no id. You return results as { role: "tool", tool_name: "list_files", content }, matched by name, which gets ambiguous when the model calls the same tool twice in one reply.
  • It streams by default.

Your clone won't use it (see ADR 0001). OpenCode doesn't either: it uses /api/tags and /api/show only to discover models.

llama.cpp: same protocol, one layer lower

llama.cpp is the inference engine; Ollama wraps an engine with a model registry, background process management, and its own API. With llama.cpp you choose the model file and the flags yourself.

  1. brew install llama.cpp (already done on this Mac: version 0.7.0, build b11669).
  2. Start the server. It downloads the same model as a GGUF file from Hugging Face on first run: 
    llama-server -hf unsloth/Qwen3.5-9B-GGUF:Q4_K_M --no-mmproj -c 32768 --port 9931
    -c 32768 sets the context (the default reads it from the model file). --no-mmproj skips the vision part you don't need. 9931 is the default port (server README).
  3. Run your unchanged loop with BASE_URL=http://127.0.0.1:9931/v1 bun index.ts.

It should just work, and that's the lesson: same protocol, different provider. What differs, as measured on this Mac:

Ollama /v1llama.cpp /v1

That reasoning field is a small, real example of "OpenAI-compatible" not meaning identical. Your loop ignores it, so it doesn't break, but an agent that displays the model's thinking would need to handle both.

Claude: the reference provider (optional, costs money)

Claude is your reference. When a local model gets something wrong, replay the same prompt here: if Claude succeeds, the local model is weak; if Claude fails too, suspect your harness. Use Claude Sonnet 5.5 (claude-sonnet-5-5). It speaks a different protocol, Anthropic Messages, so you need a second loop:

Sources: Tool use overview, Handle tool calls. Set anthropic-version: 2023-06-01 and read your key from ANTHROPIC_API_KEY.

Write the Claude loop as a separate file and notice how much of it is copied from the local one. That duplication is deliberate. Lesson 4 removes it.

If you have 32 GB or more (your M4) Raise the context to 65536 on both servers, as Ollama recommends for agents. Keep qwen3.5:9b as the baseline so results compare across your two Macs, and try a larger local model only as a free second reference.
Tangible win The same 30-line loop runs against two different local providers by changing one URL. Everything from here is "how do we make this loop trustworthy", not "what is the loop".

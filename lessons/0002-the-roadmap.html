Coding an AI Agent · Part 2

The Roadmap

The Part 1 agent works and has five specific weaknesses. Each part of this series addresses one of them. This post gives the order and the reasoning.

Start from what breaks

The loop built in Part 1 is a real agent, and it has limits. Before the map, here are the five ways it fails:

  1. Its capabilities are limited. Three tools: list_files, read_file and edit_file. If one of them throws, for example on a path that doesn't exist, the program crashes instead of telling the model what went wrong.
  2. You can't test it. Every run needs a live model: seconds per step locally, money per step on Claude, and a different answer each time. Errors are invisible in the types: nothing tells you list_files can fail.
  3. It forgets everything. Your messages array lives in memory. Press Ctrl-C and the conversation is gone.
  4. It has no guardrails. Add a bash tool and the model can run any command it proposes. Nothing stands between the proposal and the execution.
  5. It speaks one protocol per file. Your local loop and your Claude loop are two near-copies. Every fix has to be made twice, and a fourth provider would mean a third copy.

Each module ahead addresses one of these. When a topic seems unmotivated, this list gives the reason it is there.

Three parts of an agent

You already met this framing in Anthropic's Managed Agents post. This framing is the basis of the roadmap:

  • Harness: the loop. Calls the model, reads its tool calls, routes each one to the right tool. Your Part 1 code is a harness.
  • Session: the durable record of what happened, stored outside the model's context window and outside your process, so it survives crashes.
  • Sandbox: where tools actually touch the world (files, shell), with guardrails on what's allowed.

The post's core argument is that these should be separate: a crashed harness resumes from the session; a sandbox can be replaced without losing history. Failures 1, 2, and 5 above are harness problems, failure 3 is a session problem, failure 4 is a sandbox problem.

The vocabulary

OpenCode uses its vocabulary consistently, and the same terms appear in every file of its source. The glossary is the canonical list; these are the six words the map uses:

  • A provider serves models over HTTP (Ollama, a llama.cpp server, Anthropic). A model is specific weights (qwen3.5:9b).
  • A protocol is a wire format (OpenAI Chat Completions, Anthropic Messages). A route binds a protocol to one provider's endpoint and auth. Ollama and llama.cpp are two routes on one protocol; which matches OpenCode's Route.make (route/protocol.ts).
  • A step is exactly one model call, from request to response. Your loop's body, once (per AGENTS.md).
  • A turn is all the steps from a user prompt until the agent goes idle. Part 1's "the loop stops when the model replies with text" is the end of a turn.

One rule from the same file will reshape your agent in Stage B: "Each step is one explicit llm.stream call that continues from reloaded history. Do not add an in-memory tool loop." The Part 1 loop is an in-memory tool loop of the kind that rule forbids. It stays as it is until Stage B, which covers why OpenCode forbids it.

The map

Stage A · Harness

Fixes failures 1, 2, and 5: a capable loop, one interface for every provider, testable without a live model.

The agent loop done

Prompt → tool call → run it → tool result → repeat, on Ollama, llama.cpp, and Claude.

Three-tool agent in plain TypeScript: list_files, read_file, edit_file.

Tools as data next

A tool registry: name, description, input schema, and executor in one object. Tool failures returned to the model as results instead of crashing the loop.

Five tools in one registry: list_files, read_file, edit_file, write_file, bash.

In OpenCode: packages/core/src/tool.ts, tool/AGENTS.md ("each tool carries its name, options, schemas, and executable behavior in one object").

Providers behind one interface

Your agent gets its own message type: a tool call is { type: "tool-call", id, name, input }, a tool result is { type: "tool-result", id, name, result }, and an error is a kind of result, not a flag. Each protocol translates to and from it, so the loop stops knowing which provider it talks to.

One loop that runs on Ollama, llama.cpp, or Claude by configuration. Adding a provider means adding a route.

In OpenCode: ai/src/schema/messages.ts (ToolCallPart, ToolResultPart), protocols/openai-compatible-chat.ts (24 lines: one protocol, many routes).

Why Effect: errors as values

Plain TS hides failure: a function's type doesn't say it throws. Effect puts the error in the type (Why Effect?). You'll rewrite your loop with Effect.gen and typed tool errors.

Same agent, Effect version, every failure visible in a type.

Services and layers

The model client and tools become services your loop asks for instead of imports. Swapping a real model for a scripted fake becomes a one-line change.

A test that runs your whole loop against a fake model. No API key, no cost.

In OpenCode: Tool.Service, Permission.Service; OpenCode's Effect skill.

Streaming

Text arrives token by token instead of all at once. Effect's Stream carries it. Both protocols stream as server-sent events, but in different event shapes, so each protocol needs its own decoder into your common type. Locally this matters most: at ~8 tokens/s on a 16 GB M1, a non-streaming reply can sit silent for half a minute.

Output appears in your terminal as the model writes it, on every provider.

In OpenCode: packages/ai/src/llm.ts. LLM.stream runs exactly one model call (ai/AGENTS.md).

Stage B · Session

Fixes failure 3: memory that outlives the process.

The session as an event log

Append every fact (prompt received, step finished, tool result) to SQLite. Before each step, reload history from the log instead of trusting an in-memory array. This is the "no in-memory tool loop" rule, made concrete.

Kill your agent mid-task, restart it, watch it continue.

In OpenCode: session/runner/step.ts, session/history.ts. Tool: bun:sqlite.

Inbox vs. execution

Saving a prompt and running the model become two separate acts. A prompt is durable the moment it's accepted, even if the process dies before the model sees it.

A queued prompt survives a crash and runs on restart.

In OpenCode: session/inbox.ts, session/execution.ts, execution/restart.ts.

Context limits and compaction

Long sessions outgrow the model's context window. Older history gets summarized, while the full log stays in the session. Local models hit this first: Ollama's 4k default overflows within a few steps (which is why Part 1 starts at 32k), and even 32k fills in a long task. Claude's much larger window delays the problem; it doesn't remove it.

A long session that keeps working instead of erroring.

In OpenCode: session/compaction.ts.

Stage C · Sandbox

Fixes failure 4: the model proposes, a policy decides, and only then does your code act.

Permissions

Ask before risky tools run. A "no" goes back to the model as a result it can react to, not as a crash.

A y/n prompt before write_file and bash; denials the model adapts to.

In OpenCode: packages/core/src/permission.ts; the decline handling described in tool/AGENTS.md.

Interruption

Ctrl-C stops the current step cleanly, without corrupting the session log. Effect's interruption model handles this.

Interrupt mid-tool-call, restart, find a consistent session.

Capstone

Defend your design

Read OpenCode's session runner end to end and write, in your own words, where your agent agrees, where it's simpler, and what that simplicity costs. This is the final exercise of the series.

Safety note for right now If you add a bash tool before Stage C, put a simple confirm()-style y/n prompt in front of it from the start. The full permission system can come later. Running arbitrary shell commands proposed by a model should not wait for it.

While you build: three predictions

Write your answers in a notes file next to your agent before you get to the matching module. Making a guess first, even a wrong one, helps retention more than reading the answer directly.

  1. Point list_files at a directory that doesn't exist. What does your loop do? What should it do? (Claude's Handle tool calls page shows how Anthropic's protocol reports a failed tool. Does the OpenAI protocol have the same thing?)
  2. Press Ctrl-C halfway through a multi-tool task. Which data was lost, and what is the smallest thing you'd need to write to disk to get it back?
  3. OpenCode reloads history before every step instead of keeping it in memory. That's slower. What does it buy them?
Result You can now look at any piece of agent code, in your agent or in OpenCode, and say which of the three parts it belongs to and which failure it prevents. This framing is used in every remaining part.

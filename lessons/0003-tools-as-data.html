Lesson 3 · Stage A · Harness

Tools as Data

Go from one hard-coded tool to a registry of four that both of your protocols can use, where a failing tool becomes information the model can act on instead of a crash.

First: your prediction

In Lesson 2 you predicted what your loop does when list_files gets a path that doesn't exist, and whether the OpenAI protocol reports failures the way Anthropic's does. Recall your answer before opening this.

What it should do, on each protocol

It should not crash, and it should not hide the failure. It should send back a normal tool result that says what went wrong. How you mark it as a failure depends on the protocol:

  • Anthropic Messages (Claude) has a flag: "is_error": true on the tool_result (Handle tool calls).
  • OpenAI Chat Completions (Ollama, llama.cpp) has no such flag. A role: "tool" message is just text, so the text is the only signal. OpenCode does the same: on this protocol an error result is simply written out as the message content (protocols/shared.ts).

This works on small local models too. On this Mac, both Ollama and llama.cpp running qwen3.5:9b received "Error: directory not found: . (try listing 'src' instead)" and immediately called list_files again with "src". A clear error message is the whole mechanism, so write it well.

A tool is one object

Every serious agent ends up with the same shape. A tool is a single value holding four things: a name, a description, an input schema, and an executor (the function that does the work). Compare Thorsten Ball's Go agent with OpenCode:

Sources: How to Build an Agent; packages/core/src/tool/plugin/read.ts. OpenCode's tool/AGENTS.md makes this a rule: "Each tool carries its name, options, schemas, and executable behavior in one object."

Notice that neither object mentions a protocol. A tool is provider-neutral. Keeping it that way is what makes tools data:

  1. Each protocol's tool list is derived from the registry. One small function turns a tool into { type: "function", function: { name, description, parameters } } for OpenAI; another turns it into { name, description, input_schema } for Anthropic. Same JSON Schema, different wrapping. You never write a definition twice.
  2. Dispatch is a lookup by name. When a tool call arrives, find the tool with that name and run its executor. A tool the model asks for that you don't have isn't a crash either: Ball's agent replies "tool not found" as an error result.

Add a fifth tool and you add one object. Neither loop changes, and neither does any protocol code. That's the tangible win of this lesson.

Three rules for tools the model can use well

1. Descriptions matter most

Claude's docs call detailed descriptions "by far the most important factor in tool performance" and recommend at least 3–4 sentences: what the tool does, when to use it (and when not to), what each parameter means, and its limits. OpenCode's read description is seven sentences long, and it tells the model how to read large files ("Use offset and limit…") and when to use a different tool ("use grep to find specific content"). Anthropic's tool-design post gives a useful test: describe the tool as you would to a new hire. The advice comes from Anthropic, but it matters more for a 9B local model, which has less ability to guess what you meant.

2. Errors should say what to do next

The docs: "Instead of generic errors such as "failed", include what went wrong and what Claude should try next." Here is OpenCode doing it. When a file is missing, the read tool doesn't return "not found". It looks for similar names: 

File not found: docs/README

Did you mean one of these?
docs/README.md

Its truncation notice works the same way: [Output truncated. Continue reading with offset: 2001]. The model gets the exact next call to make. On your local providers, where there's no error flag, this text is everything.

3. Model input is untrusted

The schema tells the model what to send, but nothing forces it to comply. Claude's docs say that when input is invalid and you reply with an error result, "Claude will retry 2–3 times with corrections before apologizing to the user." Local models make this mistake more often, and the OpenAI protocol adds one more way to fail: arguments arrives as a JSON string, so JSON.parse itself can throw on a malformed reply. Treat a parse failure like any other bad input: an instructive error result, never a crash. OpenCode's registry validates model input at runtime for every tool (tool/AGENTS.md, Registration). In the Effect lesson, Schema will do this for you. For now, check it by hand.

FailureNo flag. Start the content with Error: and say what to try next.
  • Keep the tool list short. Every definition costs context on every step, and a 32k window is small. Anthropic's tool-design advice ("more tools don't always lead to better outcomes") applies doubly here.
  • llama.cpp picks a tool-call format from the model's chat template. When it doesn't recognize the template it falls back to a generic format that "may consume more tokens and be less efficient" (function-calling.md). If tool calls misbehave on llama.cpp but not Ollama, check the chat format in the server's startup log.
  • Ollama's OpenAI endpoint doesn't support tool_choice, so you can't force a tool call there (OpenAI compatibility). Steer with the prompt and descriptions instead.

Failureis_error: true, plus the same instructive text

Two Claude-only extras: strict: true on a tool definition makes Claude's calls always match your schema (Define tools), and Claude is your reference. When a local model keeps calling a tool wrong, run the same prompt and tools against Claude. If Claude gets it right, improve the description or accept the model's limit. If Claude gets it wrong too, the problem is probably your definition or your dispatch.

Your turn: build the registry

In your agent repo, on Ollama first. Still plain TypeScript and fetch; Effect comes after the provider lesson.

  1. Define the provider-neutral shape once: 
    type Tool = {
  name: string
  description: string
  parameters: Record<string, unknown> // JSON Schema, shared by both protocols
  execute: (input: unknown) => Promise<string>
}
    Make list_files the first value of this type, and keep a const tools: Tool[].
  2. Write toOpenAITool(tool) and use it with map to build the tools parameter for Ollama and llama.cpp.
  3. Write one runTool(name, rawArguments) that returns { content: string, isError: boolean }. It looks the tool up, parses the arguments (a JSON string on OpenAI), and catches everything: unknown tool, bad JSON, bad input, a throwing executor. Your OpenAI loop sends content in the role: "tool" message, starting it with Error: when isError is true.
  4. Add read_file, write_file, and bash. Give each a description of at least three sentences. Check inputs by hand inside each execute (for example, throw "path must be a string, e.g. src/index.ts").
  5. Put a y/n confirmation in front of bash and write_file before running them (Lesson 2's safety note). If the user answers no, return an error result with "User declined". That's a small preview of Stage C.
  6. Prove it works: ask the agent to read a file that doesn't exist. You should see the error go out and the model react to it (try another path, or explain the problem) instead of the program crashing. Then run the same prompt with BASE_URL pointed at llama.cpp.
  7. Claude (optional): write toAnthropicTool(tool), reuse the same runTool, and in your Claude loop map isError to is_error. Notice what you wrote twice: the loop, and the translation in and out. That's Lesson 4's job.
Watch for this With four tools, a model may request several tools in one reply. Every call needs its own result. On the OpenAI protocol that's one role: "tool" message per call, right after the assistant message. On Anthropic it's one user message whose content starts with all the tool_result blocks. A 400 error mentioning "tool_use ids were found without tool_result blocks" means you got this wrong.
If you have 32 GB or more (your M4) A larger local model will make fewer malformed calls. Try it as a free second reference before reaching for Claude, but keep building against qwen3.5:9b: code that handles a small model's mistakes handles everyone's.
Tangible win Adding a tool now means adding one object, and it works on every provider at once. Your tools no longer depend on your loops, and that independence is what lets OpenCode accept tools from plugins and MCP servers it has never seen.

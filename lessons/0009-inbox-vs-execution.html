Inbox vs. Execution

A prompt typed while the agent is busy, or left behind by a crash, should not be lost. This post saves each prompt in SQLite the moment it is typed and runs it later, so it waits its turn and survives a restart.

A prompt typed while the agent is busy

Suppose the agent is in the middle of a refactor. It has read a dozen files, edited three of them, and started the test suite, which will take a few minutes. While it works, the user remembers one more thing and types a second line: "also update the changelog". A moment later the terminal is closed, or the laptop goes to sleep and the process is killed.

With the agent from Part 8, that second line is gone. Nothing was reading the keyboard while the turn ran, so the line was sitting in the terminal's own input buffer, outside the program. The log from Part 8 is durable, but it starts at the moment the agent takes a prompt. Everything the user handed over before that moment depends on the process staying alive.

This post closes that gap. The goal is that a prompt is safe the instant the user hands it over, whether or not the agent can do anything with it yet. A mail slot in a door works this way: a letter that drops through the slot is delivered, whether or not anyone is home to read it, and reading it is a separate act that happens later. For the agent, accepting a prompt becomes its own step, a write to the SQLite file, and running a prompt becomes a second step that starts when the agent is free. OpenCode's AGENTS.md states the rule as "Keep durable prompt admission separate from model execution" (AGENTS.md).

Why this belongs to the session

Anthropic's post on Managed Agents, which Part 2 introduced, describes the session as the append-only log of everything that happened, kept apart from the loop that calls the model. The point of that split is stated plainly: nothing in the loop needs to survive a crash, because a new loop can start from the log and resume from the last event. Part 8 built that log for what the agent did. This part applies the same thought to what the user asked.

The other post from Part 1, Building effective agents, notes that agents "can pause for human feedback at checkpoints or when encountering blockers". Human input arrives at the human's pace and not at the agent's. A user types while a tool runs, thinks of a correction a minute after pressing Enter, or sends three requests in a row. For an agent that listens only between turns, each of those is a chance to lose the line. An agent with an inbox keeps it.

The agent changes in four places. A new table holds the prompts that wait. The session gets methods to put a prompt into it and take one out. The terminal learns to share the keyboard between two readers. And the REPL, the read-eval-print loop that reads a line, runs a turn on it, prints the output and asks again, splits into a part that accepts prompts and a part that runs them.

The inbox

Four words

The glossary has four new terms. The inbox holds the prompts a session has accepted and not yet run, oldest first. To admit a prompt is to put it into the inbox. To deliver a prompt is to move the oldest one out of the inbox and into the event log as a prompt event, which starts a turn. A wake is a signal that tells the agent to look at the inbox. A prompt is always in exactly one of two places, the inbox or the event log, and never in both.

Six decisions in the design

1. A prompt is in the inbox or in the log, and the log keeps its meaning

The event log from Part 8 records facts that happened: the user said this, the model answered that. A prompt that waits has not been answered by anyone yet, so it is not that kind of fact. The inbox is a second table with one row per waiting prompt, and a row is deleted when its prompt is delivered. The table is a to-do list, and the log is the record of what was done.

The other way to do this is to add two events to the log, "prompt queued" and "prompt delivered", and work out the waiting prompts by folding the log. That would need no second table. It would also make accepting a prompt a write to the log, whose event numbers are counted by one writer (Part 8), and it would put prompts in the log that the model has not yet seen. OpenCode keeps a separate table for the same reason. Its AGENTS.md says: "Session.prompt(...) publishes session.inbox.enqueued, whose projection inserts one durable session_inbox row [...] session_inbox stores only unconsumed work" (AGENTS.md).

2. Delivery is one transaction

Delivering a prompt takes two statements: delete the row from the inbox, and insert the prompt event into the log. A transaction is a group of statements that SQLite applies as a whole or not at all, even if the process is killed in the middle. Without one, a kill between the two statements has two possible outcomes. If the delete came first, the prompt is in neither place and is lost. If the insert came first, the prompt is in both and runs twice.

With the two statements in one transaction, the prompt is in the inbox or in the log at every moment. OpenCode does the same with its own tables: "Delivery publishes session.inbox.delivered; its projection consumes the inbox row and inserts the visible message in the same transaction" (same paragraph of AGENTS.md).

3. The wake is a hint, and the inbox is the truth

When a prompt is admitted, the part of the agent that runs prompts has to find out. That is the job of the wake. The wake carries no prompt. It means "look at the inbox", and the prompt itself is in the table. Two consequences follow. Several wakes in a row can be merged into one, because the worker reads the inbox until it is empty anyway. And a missed wake does no harm, because the worker looks again after every turn, and at startup it looks at everything that was left behind.

OpenCode uses the same word and the same idea. Its execution service has a method wake with the comment "Registers newly recorded work. Repeated wakeups may coalesce" (session/execution.ts). In the agent here the wake is a small Effect Queue that holds at most one item.

4. One prompt per turn, oldest first, and only when the agent is idle

The worker delivers a prompt only after the previous turn has ended. A prompt typed in the middle of a turn waits, so the model never finds a new user message in the history halfway through its own work. OpenCode names this delivery mode "queue". It has a second mode, "steer", that delivers a prompt at a step boundary inside a running turn, and in OpenCode prompts steer by default (AGENTS.md, session/inbox.ts). The agent here has only the first mode.

5. A reader and a worker

The REPL splits in two halves that do not wait for each other. The reader asks for a line, admits it, rings the wake and asks again. It never waits for the model. The worker first finishes an interrupted turn, the way Part 8 does, and then repeats: deliver the oldest prompt, run its turn, and when the inbox is empty wait for a wake.

Each half runs as a fiber, which is Effect's lightweight thread: an independent task that the runtime pauses while it waits for something and resumes later. The program ends when the input has ended and the inbox is empty, so the worker finishes the queued prompts first. One detail matters for that rule. The worker reads the flag "input has ended" before it delivers. If it read the flag after, a prompt admitted just before the end could be missed: the delivery finds the inbox empty, the reader admits the last prompt and ends the input, and the worker sees the flag set and quits without running it.

6. The terminal gives each line to the newest question

Two parts of the agent can now ask the user something at the same time: the reader, with You: , and a tool that needs approval, with Allow: ... [y/N]. The terminal from Part 8 used readline's question for both, and two things go wrong with that under Bun 1.4.4. When two questions are open, the first line typed goes to the older one, so a y meant for the approval would be admitted as a new prompt. And a line that arrives while no question is open is dropped, so when several lines are piped in, only the first one is read.

The fix is a small router, makeLines. It keeps lines that nobody has asked for yet, hands a line to the newest open question (the one printed last is the one the user is answering), and fails all open questions when the input ends. The Terminal service keeps the same three methods, so nothing that uses it changes.

What this leaves for later

A prompt that always kills the process is delivered once and then resumed on every start, so the agent can crash in a loop. Part 8's resume has the same limit. A line typed while the model is streaming appears after the You: prompt that is already on screen, in the middle of the reply. Steering a running turn is not built. And a session never shrinks, so a long task will eventually outgrow the model's context window, which is Part 10.

The inbox is declared next to the event table. Open src/db/schema.ts and add this at the bottom of the file, after EventTable. The imports at the top already cover it. Each row is one waiting prompt: 

// The inbox: the prompts a session has accepted and not yet run. A row is deleted when its prompt is delivered.
// `id` counts up, so the lowest id is the oldest prompt.
export const InboxTable = sqliteTable("inbox", {
  id: integer().primaryKey({ autoIncrement: true }),
  session_id: text().notNull(),
  text: text().notNull(),
})
  1. InboxTable is a second table in the same SQLite file as EventTable, so one transaction can touch both.
  2. id is an integer that the database fills in and counts up (autoIncrement). Because it only grows, the row with the lowest id is the oldest prompt, and that is the order of delivery.
  3. session_id says which session the prompt belongs to, as in the event table, so one file can hold the inboxes of several sessions.
  4. text is the prompt itself. There is no column for a time or a status: a row exists while the prompt waits, and it is deleted when the prompt is delivered.

Step 2: Admit, deliver and pending

The agent needs three new things from its session. All of the changes in this step are in src/session.ts, which exists from Part 8. First, in the import from drizzle-orm near the top, add count to the list, since pending uses it: 

import { asc, count, eq, max } from "drizzle-orm"

Next, find the Session class and replace it, comment and all, with the version below. It is the service definition with the three new members and what each promises: 

// What the agent needs from its session: accept prompts, append facts, and read the facts back.
export class Session extends Context.Service<
  Session,
  {
    readonly id: string
    // Saves a prompt in the inbox. From this moment it survives a restart, whether or not the model ever sees it.
    readonly admit: (text: string) => Effect.Effect<void>
    // Moves the oldest prompt out of the inbox and into the log as a `prompt` event, in one indivisible act.
    // Returns its text, or undefined when the inbox is empty.
    readonly deliver: Effect.Effect<string | undefined>
    // How many prompts wait in the inbox.
    readonly pending: Effect.Effect<number>
    readonly append: (event: SessionEvent) => Effect.Effect<void>
    // Every call reads the log again.
    readonly events: Effect.Effect<SessionEvent[], SessionCorrupt>
    readonly history: Effect.Effect<Message[], SessionCorrupt>
  }
>()("@agent/Session") {}
  1. admit takes the text of a prompt and writes it to the inbox. When the Effect has finished, the prompt is in the file. Nothing in its type can fail, because a disk failure is a defect, as it is for append.
  2. deliver is an Effect and not a function. Each time it runs, it moves the oldest prompt of this session from the inbox to the log and returns its text, or returns undefined when there is nothing to deliver.
  3. pending counts the rows in the inbox of this session. The agent uses it once, at startup, to tell the user what an earlier run left behind.
  4. The rest of the service is as in Part 8. The comments on the three new members are the contract the tests in step 3 check.

The implementation is also in src/session.ts, inside the generator of SessionLive. Find the line return Session.of({ id: options.id, append, events, history: Effect.map(events, toHistory) }) at the end of the generator. Replace that one line with the code below, which defines the new pieces first and then returns the service with the three new members added. The code uses thisInbox as a second condition next to thisSession: 

      const thisInbox = eq(InboxTable.session_id, options.id)

      const admit = (text: string) =>
        db.insert(InboxTable).values({ session_id: options.id, text }).pipe(Effect.asVoid, Effect.orDie)

      // Deleting the inbox row and inserting the `prompt` event happen in one transaction: both take effect,
      // or neither does. A crash between the two statements cannot lose the prompt or deliver it twice.
      const deliver = Effect.suspend(() => {
        const next = seq + 1
        return db
          .transaction((tx) =>
            Effect.gen(function* () {
              const [oldest] = yield* tx.select().from(InboxTable).where(thisInbox).orderBy(asc(InboxTable.id)).limit(1)
              if (!oldest) return undefined
              yield* tx.delete(InboxTable).where(eq(InboxTable.id, oldest.id))
              yield* tx
                .insert(EventTable)
                .values({ session_id: options.id, seq: next, type: "prompt", data: encode({ type: "prompt", text: oldest.text }) })
              return oldest.text
            }),
          )
          .pipe(
            // The number is used up only once the transaction has committed.
            Effect.tap((text) =>
              Effect.sync(() => {
                if (text !== undefined) seq = next
              }),
            ),
            Effect.orDie,
          )
      })

      const pending = db.select({ waiting: count() }).from(InboxTable).where(thisInbox).pipe(
        Effect.map(([row]) => row?.waiting ?? 0),
        Effect.orDie,
      )

      return Session.of({ id: options.id, admit, deliver, pending, append, events, history: Effect.map(events, toHistory) })
  1. thisInbox is the condition "this session's rows", defined once like thisSession and used by the three queries.
  2. admit is one insert. The id and the order come from the database.
  3. deliver starts with const next = seq + 1, the number the new prompt event will have. The counter itself is not moved yet.
  4. db.transaction runs the generator it is given inside a SQLite transaction. The generator reads the oldest inbox row of this session, deletes it, inserts the prompt event with the number next, and returns the text. If the inbox is empty it returns undefined and changes nothing.
  5. If any statement throws, SQLite undoes the others, and the Effect fails. The failure is turned into a defect by Effect.orDie, like every other disk problem.
  6. The counter seq is set to next only after the transaction has committed. A delivery that is undone does not use up a number, so the log has no gap.
  7. pending is a count(*) over this session's inbox rows.
  8. Session.of now returns the three new members next to the old ones.

src/session.ts

import { SqliteClient } from "@effect/sql-sqlite-bun"
import { asc, count, eq, max } from "drizzle-orm"
import * as SQLiteBunDrizzle from "drizzle-orm/effect-sqlite-bun"
import { migrate } from "drizzle-orm/effect-sqlite-bun/migrator"
import { Context, Effect, Layer, Schema } from "effect"
import { SessionCorrupt } from "./errors"
import { toHistory } from "./history"
import type { Message } from "./messages"
import { SessionEvent } from "./session-event"
import { EventTable, InboxTable } from "./db/schema"

// What the agent needs from its session: accept prompts, append facts, and read the facts back.
export class Session extends Context.Service<
  Session,
  {
    readonly id: string
    // Saves a prompt in the inbox. From this moment it survives a restart, whether or not the model ever sees it.
    readonly admit: (text: string) => Effect.Effect<void>
    // Moves the oldest prompt out of the inbox and into the log as a `prompt` event, in one indivisible act.
    // Returns its text, or undefined when the inbox is empty.
    readonly deliver: Effect.Effect<string | undefined>
    // How many prompts wait in the inbox.
    readonly pending: Effect.Effect<number>
    readonly append: (event: SessionEvent) => Effect.Effect<void>
    // Every call reads the log again.
    readonly events: Effect.Effect<SessionEvent[], SessionCorrupt>
    readonly history: Effect.Effect<Message[], SessionCorrupt>
  }
>()("@agent/Session") {}

const migrationsFolder = new URL("../drizzle", import.meta.url).pathname
const decode = Schema.decodeUnknownEffect(SessionEvent)
const encode = Schema.encodeSync(SessionEvent)

// The real session: a SQLite file. Building the layer opens the file and applies the migrations;
// the end of the program closes it. A disk failure is a defect, not something the agent can handle.
export const SessionLive = (options: { path: string; id: string }) =>
  Layer.effect(
    Session,
    Effect.gen(function* () {
      const db = yield* SQLiteBunDrizzle.makeWithDefaults()
      yield* migrate(db, { migrationsFolder })

      const thisSession = eq(EventTable.session_id, options.id)
      const thisInbox = eq(InboxTable.session_id, options.id)

      // The numbering continues where the log stops. One process writes a session, so it can count for itself.
      const [last] = yield* db.select({ seq: max(EventTable.seq) }).from(EventTable).where(thisSession)
      let seq = last?.seq ?? 0

      // A row that no longer matches the schema stops the read and says which event it was.
      const readEvent = (row: typeof EventTable.$inferSelect) =>
        decode(row.data).pipe(
          Effect.mapError((error) => new SessionCorrupt({ session: options.id, seq: row.seq, problem: error.message })),
        )

      const events = db.select().from(EventTable).where(thisSession).orderBy(asc(EventTable.seq)).pipe(
        Effect.flatMap(Effect.forEach(readEvent)),
        Effect.catchTag("EffectDrizzleQueryError", Effect.die),
      )

      const append = (event: SessionEvent) =>
        Effect.suspend(() =>
          db.insert(EventTable).values({ session_id: options.id, seq: ++seq, type: event.type, data: encode(event) }),
        ).pipe(Effect.asVoid, Effect.orDie)

      const admit = (text: string) =>
        db.insert(InboxTable).values({ session_id: options.id, text }).pipe(Effect.asVoid, Effect.orDie)

      // Deleting the inbox row and inserting the `prompt` event happen in one transaction: both take effect,
      // or neither does. A crash between the two statements cannot lose the prompt or deliver it twice.
      const deliver = Effect.suspend(() => {
        const next = seq + 1
        return db
          .transaction((tx) =>
            Effect.gen(function* () {
              const [oldest] = yield* tx.select().from(InboxTable).where(thisInbox).orderBy(asc(InboxTable.id)).limit(1)
              if (!oldest) return undefined
              yield* tx.delete(InboxTable).where(eq(InboxTable.id, oldest.id))
              yield* tx
                .insert(EventTable)
                .values({ session_id: options.id, seq: next, type: "prompt", data: encode({ type: "prompt", text: oldest.text }) })
              return oldest.text
            }),
          )
          .pipe(
            // The number is used up only once the transaction has committed.
            Effect.tap((text) =>
              Effect.sync(() => {
                if (text !== undefined) seq = next
              }),
            ),
            Effect.orDie,
          )
      })

      const pending = db.select({ waiting: count() }).from(InboxTable).where(thisInbox).pipe(
        Effect.map(([row]) => row?.waiting ?? 0),
        Effect.orDie,
      )

      return Session.of({ id: options.id, admit, deliver, pending, append, events, history: Effect.map(events, toHistory) })
    }).pipe(Effect.orDie),
  ).pipe(Layer.provide(SqliteClient.layer({ filename: options.path }).pipe(Layer.orDie)))

import { Effect } from "effect"
import { InputClosed } from "./errors"

// Hands the lines the user types to whoever is asking for one.
// - A line that arrives while nobody is asking waits, and the next question receives it.
// - When several questions are open, the newest one receives the line: it was printed last, so it is the one being answered.
// - When input ends, every open question fails with InputClosed, and so does every later one once the waiting lines are used up.
export interface Lines {
  readonly push: (line: string) => void
  readonly end: () => void
  readonly next: Effect.Effect<string, InputClosed>
}

export const makeLines = (): Lines => {
  const waiting: string[] = []
  const asking: Array<(answer: Effect.Effect<string, InputClosed>) => void> = []
  let ended = false

  return {
    push: (line) => {
      const asker = asking.pop()
      if (asker) asker(Effect.succeed(line))
      else waiting.push(line)
    },
    end: () => {
      ended = true
      for (const asker of asking.splice(0)) asker(Effect.fail(new InputClosed()))
    },
    next: Effect.callback<string, InputClosed>((resume) => {
      const line = waiting.shift()
      if (line !== undefined) return resume(Effect.succeed(line))
      if (ended) return resume(Effect.fail(new InputClosed()))
      asking.push(resume)
      // A question that is interrupted stops asking, so it cannot take a line meant for the next one.
      return Effect.sync(() => {
        const index = asking.indexOf(resume)
        if (index >= 0) asking.splice(index, 1)
      })
    }),
  }
}
  1. Lines has three parts. push is called with each line that was typed, end is called once when the input ends, and next is an Effect that produces one line, or fails with InputClosed.
  2. waiting holds lines that arrived when nobody was asking. asking holds one callback for each open question, oldest first. ended remembers that the input is over.
  3. push takes the newest open question with asking.pop() and gives it the line. If no question is open, the line goes to the back of waiting.
  4. end marks the input as ended and fails every open question with InputClosed, the error that Part 5 introduced for this case.
  5. next first looks at waiting, so lines typed ahead are used in order. After that, if the input has ended, it fails. Otherwise it registers itself as an open question.
  6. Effect.callback builds an Effect from a function that calls resume later. The Effect it returns from the function is the cleanup, which runs if the question is interrupted. It removes the question from asking, so an interrupted question cannot take a line that belongs to the next one.

  3. At the bottom of the file, replace the whole repl, from its comment to the last line of the file, with the code below. The small function queued goes just above it.
const queued = (count: number) => `${count} queued prompt${count === 1 ? "" : "s"}`

// The read-eval-print loop, in two halves that do not wait for each other.
// - The reader asks for a line, saves it in the inbox, and asks again, even while a turn is running.
// - The worker finishes an interrupted turn, then delivers one prompt at a time and runs its turn.
// The reader rings a bell after each prompt. The ring carries no prompt: it only tells the worker to look at the inbox.
export const repl = Effect.gen(function* () {
  const terminal = yield* Terminal
  const session = yield* Session

  // A turn that fails is recorded as failed, so the next prompt starts from a consistent history.
  const failed = (label: string, reason: string) =>
    session.append({ type: "turn-failed", reason }).pipe(Effect.andThen(terminal.say(`[${label}] ${reason}`)))
  const guarded = <R>(work: Effect.Effect<void, ProviderError | SessionCorrupt | InputClosed, R>) =>
    work.pipe(
      Effect.catchTag("ProviderError", (error) => failed("provider error", error.message)),
      Effect.catchDefect((defect) => failed("bug", messageOf(defect))),
    )

  // At most one ring waits at a time: two rings in a row mean the same thing as one.
  const wake = yield* Queue.dropping<void>(1)
  let inputEnded = false

  const reader = Effect.gen(function* () {
    while (true) {
      const input = yield* terminal.ask("You: ")
      yield* session.admit(input)
      yield* terminal.say("[queued]")
      yield* Queue.offer(wake, undefined)
    }
  }).pipe(
    Effect.catchTag("InputClosed", () => Effect.sync(() => void (inputEnded = true))),
    Effect.andThen(Queue.offer(wake, undefined)),
  )

  // What the last run left in the inbox, counted before the reader can add anything.
  const left = yield* session.pending
  if (left > 0) yield* terminal.say(`[${queued(left)} from an earlier run]`)

  yield* Effect.forkChild(reader)
  yield* guarded(resume)

  while (true) {
    // Read before delivering: a prompt admitted before the input ended is then always found by the delivery below.
    const ended = inputEnded
    if ((yield* session.deliver) !== undefined) {
      yield* guarded(run)
      continue
    }
    if (ended) return
    yield* Queue.take(wake)
  }
})
  1. queued only builds the words "1 queued prompt" or "2 queued prompts".
  2. failed and guarded are as in Part 8: a provider error or a defect during a turn is recorded as turn-failed, and the loop goes on.
  3. wake is a queue that holds at most one item (Queue.dropping(1)). Offering to a full queue does nothing, which is the merging of wakes from decision 3. inputEnded is a plain flag.
  4. The reader loops: ask, admit, print [queued], ring the wake. Admitting comes before the acknowledgement, so [queued] means the prompt is in the file.

import { messageOf, type InputClosed, type ProviderError, type SessionCorrupt } from "./errors"
import type { FinishReason } from "./events"
import { unansweredCalls } from "./history"
import { isToolCall, type Message, type Part } from "./messages"
import { ModelClient } from "./model-client"

import { Terminal } from "./terminal"
import { runTool, Tools, type Tool } from "./tool"

// One step: reload the history from the log, stream the model's events, show the text as it arrives,
// and append the finished message to the log.
const step = (tools: Tool[]) =>
  Effect.gen(function* () {
    const model = yield* ModelClient
    const terminal = yield* Terminal
    const session = yield* Session
    const history = yield* session.history
    const content: Part[] = []
    let text = "" // the text block being written, if any
    const outcome: { finish: FinishReason; native?: unknown } = { finish: "stop" }

    // A text block ends when anything else arrives, or when the stream does, even by failing.
    const endText = Effect.suspend(() => {
      if (!text) return Effect.void
      content.push({ type: "text", text })
      text = ""
      return terminal.say("")
    })

    yield* Stream.runForEach(model.chat(history, tools), (event) =>
      Effect.gen(function* () {
        if (event.type === "text-delta") {
          if (!text) yield* terminal.write("Agent: ")
          text += event.text
          yield* terminal.write(event.text)
          return
        }
        yield* endText
        if (event.type === "tool-call") content.push(event)
        else {
          outcome.finish = event.reason
          outcome.native = event.native
        }
      }),
    ).pipe(Effect.ensuring(endText))

    const message: Message = { role: "assistant", content, ...(outcome.native === undefined ? {} : { native: outcome.native }) }
    yield* session.append({ type: "step-finished", message, finish: outcome.finish })
    return { message, finish: outcome.finish }
  })

// Steps until the model stops asking for tools. Each result is appended as soon as its tool finishes.
const run = Effect.gen(function* () {
  const terminal = yield* Terminal
  const session = yield* Session
  const tools = yield* Tools

  while (true) {
    const { message, finish } = yield* step(tools)
    if (finish !== "tool-calls") return

    for (const call of message.content.filter(isToolCall)) {
      yield* terminal.say(`[tool] ${call.name}(${JSON.stringify(call.input)})`)
      const part = yield* runTool(call)
      if (part.result.type === "error") yield* terminal.say(`[error] ${part.result.value}`)
      yield* session.append({ type: "tool-result", part })
    }
  }
})

const interrupted =
  "The agent stopped before this tool finished, so it may or may not have run. Check the current state before repeating it."

// A restart can find a turn that did not finish. Tool calls without a result get an error result instead of
// running again, since a command that already ran must not run twice. Then the turn continues.
const resume = Effect.gen(function* () {
  const terminal = yield* Terminal
  const session = yield* Session
  const calls = unansweredCalls(yield* session.history)
  if (calls === undefined) return

  yield* terminal.say(`[resuming session ${session.id}]`)
  for (const call of calls) {
    yield* terminal.say(`[interrupted] ${call.name}(${JSON.stringify(call.input)})`)
    yield* session.append({
      type: "tool-result",
      part: { type: "tool-result", id: call.id, name: call.name, result: { type: "error", value: interrupted } },
    })
  }
  yield* run
})

const queued = (count: number) => `${count} queued prompt${count === 1 ? "" : "s"}`

// The read-eval-print loop, in two halves that do not wait for each other.
// - The reader asks for a line, saves it in the inbox, and asks again, even while a turn is running.
// - The worker finishes an interrupted turn, then delivers one prompt at a time and runs its turn.
// The reader rings a bell after each prompt. The ring carries no prompt: it only tells the worker to look at the inbox.
export const repl = Effect.gen(function* () {
  const terminal = yield* Terminal
  const session = yield* Session

  // A turn that fails is recorded as failed, so the next prompt starts from a consistent history.
  const failed = (label: string, reason: string) =>
    session.append({ type: "turn-failed", reason }).pipe(Effect.andThen(terminal.say(`[${label}] ${reason}`)))
  const guarded = <R>(work: Effect.Effect<void, ProviderError | SessionCorrupt | InputClosed, R>) =>
    work.pipe(
      Effect.catchTag("ProviderError", (error) => failed("provider error", error.message)),
      Effect.catchDefect((defect) => failed("bug", messageOf(defect))),
    )

  // At most one ring waits at a time: two rings in a row mean the same thing as one.
  const wake = yield* Queue.dropping<void>(1)
  let inputEnded = false

  const reader = Effect.gen(function* () {
    while (true) {
      const input = yield* terminal.ask("You: ")
      yield* session.admit(input)
      yield* terminal.say("[queued]")
      yield* Queue.offer(wake, undefined)
    }
  }).pipe(
    Effect.catchTag("InputClosed", () => Effect.sync(() => void (inputEnded = true))),
    Effect.andThen(Queue.offer(wake, undefined)),
  )

  // What the last run left in the inbox, counted before the reader can add anything.
  const left = yield* session.pending
  if (left > 0) yield* terminal.say(`[${queued(left)} from an earlier run]`)

  yield* Effect.forkChild(reader)
  yield* guarded(resume)

  while (true) {
    // Read before delivering: a prompt admitted before the input ended is then always found by the delivery below.
    const ended = inputEnded
    if ((yield* session.deliver) !== undefined) {
      yield* guarded(run)
      continue
    }
    if (ended) return
    yield* Queue.take(wake)
  }
})

Possible extensions

Three small additions fit the design and are not built here:

  • Idempotent admission. admit could take an id from the caller and ignore a second admission with the same id. A client that retries a submit after a timeout would then not queue the same prompt twice. OpenCode works this way: reusing an inbox item id is idempotent, and the first admission wins.
  • Cancelling a waiting prompt. Since the inbox is a table, a prompt can be removed from it before it is delivered. A cancel(id) that deletes the row, and a way to list the rows with their ids, would be enough.
  • A line editor. The terminal could redraw the You: prompt and the text typed so far after each piece of output, so a reply no longer lands in the middle of a line being typed. That is a terminal user interface feature, and it would also bring back the arrow keys that readline's editing used to provide.

OpenCode does more

Three things are left out on purpose. Execution claims: OpenCode writes a claim when a turn starts and releases it when the turn ends, so a claim that is still there on startup means a process died in the middle of a turn. The agent here finds the same thing from the shape of the log, with unansweredCalls, which is enough for one process and one session. Steering: a prompt can be delivered at a step boundary inside a running turn. An attempts budget: a turn that keeps killing the process would be resumed forever, so OpenCode counts the resumes of each turn and, after maxAttempts (10 by default), marks the turn as failed instead (session/execution/restart.ts). The same file states the guarantee: recovery is at-least-once, and it does not prevent repeated external side effects after a crash (comment).

import { Effect } from "effect"
import { InputClosed } from "./errors"

// Hands the lines the user types to whoever is asking for one.
// - A line that arrives while nobody is asking waits, and the next question receives it.
// - When several questions are open, the newest one receives the line: it was printed last, so it is the one being answered.
// - When input ends, every open question fails with InputClosed, and so does every later one once the waiting lines are used up.
export interface Lines {
  readonly push: (line: string) => void
  readonly end: () => void
  readonly next: Effect.Effect<string, InputClosed>
}

export const makeLines = (): Lines => {
  const waiting: string[] = []
  const asking: Array<(answer: Effect.Effect<string, InputClosed>) => void> = []
  let ended = false

  return {
    push: (line) => {
      const asker = asking.pop()
      if (asker) asker(Effect.succeed(line))
      else waiting.push(line)
    },
    end: () => {
      ended = true
      for (const asker of asking.splice(0)) asker(Effect.fail(new InputClosed()))
    },
    next: Effect.callback<string, InputClosed>((resume) => {
      const line = waiting.shift()
      if (line !== undefined) return resume(Effect.succeed(line))
      if (ended) return resume(Effect.fail(new InputClosed()))
      asking.push(resume)
      // A question that is interrupted stops asking, so it cannot take a line meant for the next one.
      return Effect.sync(() => {
        const index = asking.indexOf(resume)
        if (index >= 0) asking.splice(index, 1)
      })
    }),
  }
}

  const terminal = yield* Terminal
  const session = yield* Session

  // A turn that fails is recorded as failed, so the next prompt starts from a consistent history.
  const failed = (label: string, reason: string) =>
    session.append({ type: "turn-failed", reason }).pipe(Effect.andThen(terminal.say(`[${label}] ${reason}`)))
  const guarded = <R>(work: Effect.Effect<void, ProviderError | SessionCorrupt | InputClosed, R>) =>
    work.pipe(
      Effect.catchTag("ProviderError", (error) => failed("provider error", error.message)),
      Effect.catchDefect((defect) => failed("bug", messageOf(defect))),
    )

  // At most one ring waits at a time: two rings in a row mean the same thing as one.
  const wake = yield* Queue.dropping<void>(1)
  let inputEnded = false

  const reader = Effect.gen(function* () {
    while (true) {
      const input = yield* terminal.ask("You: ")
      yield* session.admit(input)
      yield* terminal.say("[queued]")
      yield* Queue.offer(wake, undefined)
    }
  }).pipe(
    Effect.catchTag("InputClosed", () => Effect.sync(() => void (inputEnded = true))),
    Effect.andThen(Queue.offer(wake, undefined)),
  )

  // What the last run left in the inbox, counted before the reader can add anything.
  const left = yield* session.pending
  if (left > 0) yield* terminal.say(`[${queued(left)} from an earlier run]`)

  yield* Effect.forkChild(reader)
  yield* guarded(resume)

  while (true) {
    // Read before delivering: a prompt admitted before the input ended is then always found by the delivery below.
    const ended = inputEnded
    if ((yield* session.deliver) !== undefined) {
      yield* guarded(run)
      continue
    }
    if (ended) return
    yield* Queue.take(wake)
  }
})

// What the scripted model streams for one step, in order. A ProviderError makes the stream fail at that point.
export type Step = Array<ModelEvent | ProviderError>

// A text reply, streamed one word at a time.
export const reply = (text: string): Step => [
  ...text.split(/(?<= )/).map((word): ModelEvent => ({ type: "text-delta", text: word })),
  { type: "finish", reason: "stop" },
]

export const callTool = (id: string, name: string, input: unknown): Step => [
  { type: "tool-call", id, name, input },
  { type: "finish", reason: "tool-calls" },
]

// A step that fails before sending anything.
export const fail = (reason: string): Step => [new ProviderError({ reason })]

// A model that follows a script and records the history it was given at each step.
// `beforeStep` runs when a step starts and holds the stream back until its promise settles.
export const scriptedModel = (steps: Step[], beforeStep?: (request: number) => Promise<void>) => {
  const requests: Message[][] = []
  const layer = Layer.succeed(
    ModelClient,
    ModelClient.of({
      chat: (history) =>
        Stream.suspend(() => {
          requests.push([...history])
          const request = requests.length
          const next = steps[request - 1] ?? fail("The script has no reply left for this step")
          const events = Stream.fromIterable(next).pipe(
            Stream.mapEffect((item) => (item instanceof ProviderError ? Effect.fail(item) : Effect.succeed(item))),
          )
          return beforeStep ? Stream.unwrap(Effect.promise(() => beforeStep(request)).pipe(Effect.as(events))) : events
        }),
    }),
  )
  return { layer, requests }
}

// A terminal where the user types the given answers, in order. An answer can be a promise, for a line the user types later.
// When the answers run out, input ends.
// Questions that start with "Allow" are answered from `confirmations` instead, so a confirmation reaches the
// tool that asked even though the reader has already taken every prompt, as the live terminal does.
// `output` holds the finished lines; `writes` holds every piece passed to `write`, in order.
export const scriptedTerminal = (answers: Array<string | Promise<string>>, confirmations: string[] = []) => {
  const output: string[] = []
  const writes: string[] = []
  const queue = [...answers]
  const confirm = [...confirmations]
  let pending = "" // text written since the last line ended
  const layer = Layer.succeed(
    Terminal,
    Terminal.of({
      ask: (prompt) =>
        Effect.suspend(() => {
          output.push(pending + prompt)
          pending = ""
          const next = (prompt.startsWith("Allow") ? confirm : queue).shift()
          if (next === undefined) return Effect.fail(new InputClosed())
          return typeof next === "string" ? Effect.succeed(next) : Effect.promise(() => next)
        }),
      say: (line) =>
        Effect.sync(() => {
          output.push(pending + line)
          pending = ""
        }),
      write: (text) =>
        Effect.sync(() => {
          writes.push(text)
          pending += text
        }),
    }),
  )
  return { layer, output, writes }
}
